# 多系统本体设计概览

基线：2026-10-19。本文是多系统业务概念的阅读入口，不另行定义需求、状态、指标公式、接口或验收规则。业务和TC以[需求详细规格](需求详细规格.md) FR-20～FR-24为准；端口、数据、事件、授权与实现契约以[技术详细规格](技术详细规格.md)第二十八章为准；开发顺序见[项目开发流程](项目开发流程.md)。

## 系统边界

一期在相互隔离的模拟系统中跑通商品、订单、售后、仓储和支付闭环，并提供主管分析与异常调查能力。各系统分别拥有记录、ID、状态、接口和事务；开发时可共用数据库实例，但业务服务不能跨系统直接读写。生产适配器按目标企业接口单独配置和验收，本地模拟成功不能表述成真实退款或生产接通。

| 系统 | 权威事实 | 关键边界 |
| --- | --- | --- |
| PIM 商品主数据 | Product、SKU及商品编码映射 | 商品身份由审核后的版本化映射统一 |
| OMS 订单 | 订单、订单明细、金额、发货和签收 | 订单状态由OMS拥有 |
| 售后 | 申请、报价、客户确认、审核和余额预留 | 审核通过不代表验收完成或资金到账 |
| WMS 仓储 | 退货授权、实收、验收及证据 | 收货与验收分开记录，模型不得写入 |
| 支付系统 | 原支付、执行操作和成功退款流水 | 只有渠道权威成功证据可记账 |
| 分析服务 | 经映射和质量检查的只读投影 | 可以重算投影，不得改写源系统事实 |

## 本体与知识图谱

本体为跨系统概念、关系、状态映射和指标定义提供共同语义；外部系统保留自己的ID，经过带有效期的映射连接到稳定业务标识。知识图谱保存适合知识问答的稳定产品关系；订单、收货和退款等动态事实继续由权威系统持有，分析以只读投影关联。统一语义不会替代权限检查、业务不变量、幂等或支付/WMS守卫；OWL用于词汇/模式表达，SHACL用于形状校验，不承诺OWL DL推理。

## 闭环与正确性

业务分别记录审核、退货验收和资金状态。需要退货的退款申请先完成授权审核，再由WMS记录实收和验收；支付协调器重新检查确认、审批、金额、原支付、余额和版本后提交退款。超时查询原操作，未知状态不按失败重付；业务数据不跨库拼成一个假事务。

指标使用版本化口径、固定窗口与源水位；先按源事实粒度去重和汇总，再映射到产品。主管默认排名候选为`return_passed_item_rate`（签收批次中在观察窗内通过WMS验收的退货件数率），但须业务/财务批准后启用，且不能简称为未加限定的“产品退货率”。`return_application_item_rate`（退货申请率）作为独立指标登记；业务/财务需确定按申请数、申请行数还是申请件数计分子，以及按申请日还是其他业务事件归属时间计算。批准前该指标不计算、不排名，查询返回blocked。两项指标分别呈现，不能混合申请、收货和验收阶段。退款明细率和退款商品金额率同样分别呈现。结果须展示分子、分母、覆盖与质量状态，并可授权下钻到源记录；出现数据不完整时，受影响产品不进入完整排名。

异常调查覆盖指标波动、跨系统状态/金额不一致、仓储/退款流程问题、服务错误、超时、队列积压和知识索引故障。调查固定查询条件、数据快照和版本，沿业务ID或trace/event因果链找首个失败点；证据不足时标记原因未确认。相关因素不能直接当作因果结论，源事实由其权威系统修订。
