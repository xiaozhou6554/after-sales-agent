# 企业智能售后服务 Agent：部署、运维与用户手册

版本日期：2026-10-21。本文记录本项目当前可验证的开发部署方式与业务使用边界；Mock 适配器和本地开发演练不代表生产系统验收。

## 1. 系统能力与用户角色

系统面向售后客户和客服人员，提供订单查询、售后对话、退款/改址确认，以及客服工作台中的工单处理和退款审核能力。高风险写操作须由服务端绑定当前身份、业务对象、报价/内容摘要和一次性确认；模型不能自行填写确认标识、越权客户范围或绕过服务端授权。

- **客户**：查看本人授权范围内的订单与售后状态；对退款报价或完整改址内容进行显式确认；使用 Agent 咨询。退款到账、真实 OMS 改址和真实通知渠道取决于企业系统适配器是否接入。
- **客服/主管**：登录工作台处理被授权范围内的工单、队列和待审核退款；内部备注受员工角色与授权范围限制，客户只获得允许公开的消息。
- **运营/开发人员**：启动依赖服务、检查健康状态、运行有范围的迁移和回归，并查看架构、安全、检索、性能与部署评估记录。

## 2. 架构与依赖方向

调用方向为 `Interface → Application → Domain`；Bootstrap 负责依赖装配；Infrastructure 实现 Application 定义的端口。Domain 不依赖 Infrastructure，Application 业务用例通过抽象端口访问数据库、模型、队列、图数据库和外部售后系统。架构扫描覆盖 288 个源文件，步骤32整改后报告 0 项跨层违规。

主要目录：

| 目录 | 责任 |
| --- | --- |
| `src/domain/` | 业务规则、状态机、实体和值对象，不调用外部设施 |
| `src/application/` | 用例、DTO、端口、授权和跨领域流程 |
| `src/infrastructure/` | MySQL/Redis/RabbitMQ/Neo4j、模型、外部系统适配器 |
| `src/interface/` | HTTP 路由与请求/响应转换 |
| `bootstrap/` | API、MCP、worker、迁移入口及具体适配器装配 |
| `migrations/` | 版本化数据库结构迁移 |
| `frontend/` | 客户端、聊天和客服工作台 |
| `tests/`、`evals/` | 回归、安全、架构测试与质量评估 |

## 3. 开发环境配置

项目 Python 环境为 Conda `model`（Python 3.10）。Docker 用于 MySQL、Redis、RabbitMQ、Neo4j；前端测试需要 Node.js。当前工作站的 Conda 解释器路径为 `D:\anaconda3\envs\model\python.exe`；其他工作站应使用其自己的环境路径。

1. 只有在项目根目录尚无 `.env` 时，才从 `.env.example` 新建 `.env`；已有 `.env` 应逐项合并，不要覆盖。
2. 设置数据库、RabbitMQ、Neo4j 凭据，`ADDRESS_ENCRYPT_KEY` 私密随机值，以及需要真实模型调用时的 `LLM_API_KEY`。不要将真实密钥写入代码、报告、截图或版本库。
3. `ADDRESS_ENCRYPT_KEY` 是 API/MCP 启动所需配置。缺失时地址加密适配器会拒绝启动；变更此密钥会影响已加密地址数据的解密能力，应按密钥轮换策略处理。
4. 将 Neo4j 查询账号配置为只读账号。开发/测试的 mock 密码不适用于生产环境。

## 4. 本地 Docker 部署

默认 Compose 只启用数据库与消息基础设施；应用和迁移使用独立 profile。

```powershell
# 启动基础设施
docker compose up -d
docker compose ps

# 仅当发布了待执行的数据库迁移、并完成数据备份与变更检查后运行
docker compose --profile migrate run --rm migrate

# 启动应用服务
docker compose --profile app up -d --build api mcp worker
docker compose --profile app ps
```

API 和 MCP 默认绑定本机回环地址，端口分别为 8000 与 8001；按需使用 `API_PORT`、`MCP_SERVER_PORT` 调整宿主机端口。容器内部 API/MCP 端口保持 8000/8001。健康探针为 `/health/live`，依赖就绪状态使用 `/health/ready`。

停止应用但保留数据库和持久卷：

```powershell
docker compose --profile app stop api mcp worker
```

不要用 `docker compose down -v` 清理持久卷，除非明确准备销毁所有本地数据库和队列数据。存在待处理 Outbox 事件时，启动 worker 前先核对事件类型、环境和处理器。步骤35先发现42条待处理事件并暂停启动；后续确认共享开发环境仅使用 Mock 处理器后，已完成开发队列恢复，最终全量回归后的13条测试事件也已发布，数据库 pending/publishing 清零并稳定5秒。Windows worker 停止码1已在步骤35报告中披露；该本地演练不代表生产恢复验收。

## 5. 本地进程开发

在已激活的 `model` 环境中，分别使用终端启动 MCP、API 和 worker；数据库与消息依赖需先健康。运行真实模型对话时需配置 `LLM_API_KEY`。

```powershell
python -m bootstrap.mcp_main
python -m bootstrap.api_main
python -m bootstrap.worker_main
```

数据库迁移由 `bootstrap.migrate` 提供入口。开发环境可按项目约定检查待迁移版本；不要在已共享的数据环境中无审查地重放迁移。前端自动化命令：

```powershell
npm.cmd test --prefix frontend
```

## 6. 用户业务流程

### 客户退款

客户在退款页提交售后对象并查看服务端资格与金额报价，核对报价后显式确认并提交。服务端执行绑定确认、权限、幂等和状态检查；存在支付/退货门槛时必须先满足。退款是否真实到账需核对支付渠道的权威回执；当前本地支付通道为 Mock，不能据此确认真实企业资金已经退回。

### 客户改址

客户通过改址表单填写新收件信息，核对脱敏摘要后完成一次性确认。原始地址只进入受控后端处理并以密文存储；客户端在成功提交或离开页面后清理原文控件。是否已向承运或 OMS 生效，应以真实 OMS 适配器返回为准；本地 Mock 状态不代表真实物流地址已改变。

### Agent 对话与人工处理

Agent 的回答由当前可用的 RAG、知识图谱和业务只读工具支撑。涉及退款、改址、工单等写操作时，必须经过相应页面和服务端确认流程。信息不完整、证据冲突或依赖不可用时，应按页面提示补充材料、重试只读查询或转人工，不要把模型生成文本当作退款到账、改址成功或员工已接单的权威凭据。

### 客服工作台

客服/主管仅可访问其服务端授权的客户、队列、工单和审核记录。员工内部备注不是客户公开消息。接单、分派、状态修改或退款审核前检查目标客户/团队、当前版本和确认摘要；发生版本冲突时重新加载页面并复核，不要重复提交旧确认。

## 7. 日常运维与故障处理

- 先查看 `docker compose ps` 与服务健康状态；API、MCP 存活但依赖未就绪时，查看 `/health/ready` 并针对 MySQL、Redis、RabbitMQ、Neo4j 做只读检查。
- 检查结构变更时先核对迁移版本，再选择性运行 `migrate` profile；应用服务不会自动替你决定是否修改共享数据库。
- Agent 异步任务和领域事件分别记录在 `agent_task`、`outbox_event`。处理积压前先检查事件状态、失败原因和幂等键，再按既定恢复流程操作。
- 不手工改写成功支付账本、退款执行状态、地址密文或审计记录来“修复”页面；通过对应业务恢复/对账流程核实权威来源。
- 运维报告和评估材料不得记录 API 密钥、真实收件地址、付款账户或未脱敏客户数据。
