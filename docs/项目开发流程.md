# 项目详细开发流程

 > 2026-10-19 重置：旧步骤及产出是重建计划，历史通过不能证明当前实现。v2静态模拟数据现已生成；评测执行器、应用和独立模拟服务仍待开发。允许基于合成数据和隔离模拟系统开始本地开发；业务/财务签字、厂商契约、安全与部署审批是生产集成和上线门槛。先实现跨系统契约，再从步骤01开始开发。05A接入v2数据与本体资产；步骤25A～25D分别实施仓储、支付、本体映射与投影、主管分析；31～36完成横向验收。真实仓储/支付适配纳入一期，具体渠道接通单独验收。


本文用于按步骤推进一期开发，说明每一步做什么、产出什么、如何验收。它是开发执行顺序，不重新定义业务规则、技术参数或接口字段。

## 一、使用方式与开发边界

- 业务范围和验收以[需求详细规格](需求详细规格.md)为准；参数、接口、数据、事务和状态以[技术详细规格](技术详细规格.md)为准。摘要仅作导航，不覆盖详细规格。
- 文件位置以[项目目录结构](项目目录结构.md)为准；环境与命令以[开发运行指南](开发运行指南.md)为准；提示词以[Prompt设计](Prompt设计.md)为准。
- 当前为开发计划，不表示业务源码、数据库、配置、测试或接口已经存在。v2静态模拟资产以及 `data/scripts/` 下的确定性生成器和离线校验器已重建；业务实现与评测执行器仍待开发。重新生成会清理并覆盖生成器管理的旧基线。
- 数据资产与数量以[模拟数据说明](模拟数据说明.md)为准。离线一致性检查不替代功能验收。
- 后端坚持 src/ 下直接设置 interface、application、domain、infrastructure 四层；bootstrap/ 位于根目录。API、MCP、Worker 分进程启动，MCP注册按领域分权的工具组。Agent基线为单一Supervisor、确定性工作流和领域用例，不为每个工具组建立自主Agent。
- 每一步的实际变更与验收证据写入版本控制提交/看板；不创建或恢复docs/开发记录。只通过编译或生成目录不算业务功能完成，不以 Mock 测试代替真实模型/真实数据库集成验证。
- 优先形成可验证的完整业务流程，再扩展能力。不一次性创建所有空文件，也不等全部数据库表设计成代码后才开始跑通订单查询。
- 不缩减一期需求；受控支付执行、真实WMS/支付适配和产品异常追查纳入一期；真实生产渠道须独立验收。提示词修改必须有明确授权，不在普通代码实现中顺手改写。
- 退款和地址修改必须经过服务端强制校验。开发测试使用隔离数据及明确标记的模拟支付适配器，不配置生产渠道或发送真实资金。真实生产渠道接入需沙箱和独立上线验收。

## 二、阶段与里程碑

| 阶段 | 步骤 | 阶段目标 | 完成标志 |
| --- | --- | --- | --- |
| A：工程与第一条业务链路 | 01～10（含05A） | 初始化、四层检查、模拟数据初始化、认证、订单 MCP、基础对话 | M1：能通过真实模型调用 MCP 查询本人 Mock 订单并回答，越权被拒绝 |
| B：会话与可靠运行 | 11～15 | 记忆、恢复、可靠消息、后台任务 | M2：重启可恢复，同一业务不重复执行，任务可追踪 |
| C：知识与完整 Agent 能力 | 16～23 | RAG 双路、KG、混合检索、物流与复杂编排 | M3：知识路由和多步骤执行有证据、预算和故障处理 |
| D：受控业务写入与多系统闭环 | 24～28（含25A～25D） | 退款申请/审核、独立WMS收货验收、受控支付、映射发布、指标投影与异常追查、改址和工单 | M4：所有写操作权限、确认、幂等、事务与跨系统恢复成立 |
| E：客户与员工界面 | 29～32 | 客户页面、确认表单和最小工作台 | M5：通过 Web 完成客户及客服售后闭环 |
| F：验收与交付 | 33～36 | 安全、评测、压测、部署及文档交付 | M6：一期范围完成，有可复现的验证与运行记录 |

阶段有先后依赖，不是互相隔离的瀑布流程：每步都应写必要测试并处理已发现问题。前端可以在接口稳定后按契约样例推进，但最终必须接真实后端验收。

## 三、逐步开发任务

### 阶段 A：工程与第一条业务链路

### 步骤 01：建立需求与开发任务映射

**前置：** 阅读 docs/ 下现有文档，确认它们是同一开发基线。

**做什么：**

1. 将 FR、BR、TC 映射到本流程步骤、所属模块及验证方式，保留原编号，不新造另一份业务范围。
2. 标识第一条订单查询流程需要的最小接口、认证上下文、查询端口、Mock 数据及 Agent 输出。
3. 身份与订单资源存在性语义按《需求详细规格》FR-01、FR-05执行；生产长期记忆类别须经业务/隐私负责人批准并遵循最少必要原则。
4. 维护`data/scenarios/v2/acceptance-test-map.csv`中的TC—场景—计划测试映射；当前131个TC均有场景记录，运行状态仍为`not_implemented`，新增的61个场景还需在应用实现后绑定可执行断言并运行。

**产出：** 需求—实现—验证映射随项目文档维护；本轮明确清空开发记录，重新开发阶段不得依赖旧记录中的已验证结论。

**如何验收：** 每项一期功能都能找到后续实现步骤和验收来源，退款、改址、KG、工作台、审计等没有遗漏；未解决事项有明确落点，不泛化为整个项目无法开发。

### 步骤 02：检查开发环境与锁定依赖

**前置：** 步骤01。

**做什么：**

1. 按开发运行指南检查 Conda model、实际 Python 路径、版本及已安装依赖，不将文档里的历史检测表当作当前事实。
2. 只选择项目实际使用的 Web、MCP、模型、数据库、消息、检索及测试依赖，检查 Windows 运行和容器运行的差异。
3. 完成最小导入与连接验证，生成 pyproject.toml 和精确版本锁文件；记录模型适配、Checkpoint、向量库的兼容结果。
4. 将真实密钥留在受控环境中，不写入源码、测试数据或版本库。

**产出位置：** pyproject.toml、requirements.lock、.gitignore、.env.example，以及开发运行指南中的实际检查结果。

**如何验收：** 在项目环境中可按锁文件安装、关键依赖可导入、依赖检查无冲突；尚未验证的组件明确标记，不写成已通过。

### 步骤 03：创建最小代码骨架与可安装入口

**前置：** 步骤02。

**做什么：**

1. 创建 src/ 下四层、根目录 bootstrap/ 和最小 tests/，添加确有需要的包初始化文件。
2. 在项目配置中明确四层包及根目录启动组装的打包方式，避免多包发现错误或安装后丢失 bootstrap。
3. 创建 API、MCP、Worker 三个入口骨架，各自组装依赖，正常关闭连接与后台资源。
4. 配置基础格式、静态检查和测试入口，不创建所有领域空聚合。

**产出位置：** src/ 四层、bootstrap/、tests/、项目配置。

**如何验收：** 从已安装项目运行入口，并从其他工作目录验证导入；不能仅依赖当前目录或临时 PYTHONPATH 才能启动。此时入口可只提供启动/健康骨架，不宣称业务完成。

### 步骤 04：建立四层与模块依赖检查

**前置：** 步骤03。

**做什么：**

1. 检查 Domain 不依赖应用、接口、基础设施或具体 SDK；Application 不导入 Interface/Infrastructure。
2. 明确 LangGraph 只允许出现在《技术详细规格》指定的应用编排区域，具体数据库 Saver 仍在基础设施层。
3. 检查接口只调用用例、Bootstrap 只组装、不跨模块导入私有仓储与聚合实现。
4. 为确有需要的公开应用端口建立显式边界，拒绝以“公共工具类”绕过分层。

**产出位置：** tests/architecture/，必要的检查配置。

**如何验收：** 合法依赖通过；临时引入一项错误依赖能被检查发现，撤销后通过。检查真实边界，不靠目录名字假定架构正确。

### 步骤 05：接入基础配置、容器依赖和数据库迁移

**前置：** 步骤03、04。

**做什么：**

1. 实现统一配置读取、类型校验、必填密钥检查及环境差异；运行参数从《技术详细规格》唯一参数表落入配置。
2. 准备本地 MySQL、Redis、RabbitMQ、Neo4j 和开发向量后端的运行配置，不强迫开发机器同时运行两套向量后端。
3. 建立 migrations/ 的版本升级机制，先创建当前步骤需要的表，之后随业务能力增加迁移。
4. 区分存活、就绪和显式降级；进程不在启动时争抢执行数据库结构升级。

**产出位置：** docker-compose.yml、bootstrap/settings.py、基础设施连接模块、migrations/、.env.example。

**如何验收：** 基础依赖可连接，初始化/重复启动行为正确；缺配置、错误凭据和依赖故障给出准确健康状态，日志不泄露连接密钥。

### 步骤 05A：统一模拟数据构建、初始化与校验（在步骤05之后执行）

**前置：** 步骤05的数据库结构与隔离配置可用；读取[数据管理入口](../data/README.md)。

**做什么：**

1. 重建生成器和离线校验脚本后，按[模拟数据说明](模拟数据说明.md)核对场景、知识图谱、固定测试时间和哈希清单。
2. 编写种子到Mock业务表的字段映射和初始化适配器，按租户/身份、客户授权、订单、关联业务记录顺序导入。表单地址按技术设计加密，可靠业务写入落MySQL。
3. 编写隔离重置和场景执行器：每例恢复种子、应用自身patches/additions，逐项实现controls。基线不混入负向测试脏数据，不从fixture直接信任身份或签发确认。
4. 对照模块建立数据使用映射：订单/物流读取业务事实；退款/改址通过运行时确认和事务操作业务表；RAG读取原文，KG读取节点关系；记忆、任务、通知、审计和工作台读取对应关联记录。
5. 评测输入只提供问题和正常业务输入，预期单独保留；记录开发/保留集划分。知识索引和Neo4j实际导入在步骤16～19完成。

**产出位置：** `data/` 现有资产与脚本、基础设施初始化/重置适配器、场景执行器和 `data/generated/reports/` 执行记录。

**如何验收：** 离线校验通过；初始化与重置可重复执行；业务外键、金额和权限映射正确；异常用例彼此隔离。未实现controls列为未执行，不能按预期标签直接判通过。


### 步骤 06：实现通用请求、响应和错误契约

**前置：** 步骤04、05。

**做什么：**

1. 按《技术详细规格》第二十六章定义 API、TraceContext、Error、业务引用、授权上下文与 MCP 信封模型。
2. 落实严格字段、枚举、空值、版本、错误映射及安全提示；将传输模型转换为应用 DTO，不传入领域层。
3. 建立正常、空、错误、部分失败、异步受理的固定契约样例。
4. 保证客户端字段不能覆盖可信身份、租户、链路或资源归属。

**产出位置：** interface/http/schemas/、interface/mcp/schemas/、application/common/、tests/contract/。

**如何验收：** 合法样例通过，未知字段、非法状态、缺字段和未知版本被拒绝；错误结构前后一致，安全错误不暴露内部异常。

### 步骤 07：实现 Mock 认证与授权

**前置：** 步骤05、05A、06。

**做什么：**

1. 创建预置客户、客服、人工客服、主管、管理员账户及隔离租户/团队/客户范围。
2. 实现 Mock 登录与可信 AuthContext，后端签发身份，客户端不能自行填写角色与 Scope。
3. 实现客户本人访问、客服代客范围和员工业务权限；保留真实操作者与目标客户的区别。
4. 让 MCP 逐次验证可信调用上下文，不因连接来自 API 就跳过最终用户授权。
5. 统一未授权资源与不存在的安全语义，补齐相关验收前提。

**产出位置：** interface/http/middleware/、认证路由、application/common/authorization.py、基础设施认证适配器、Mock 身份数据。

**如何验收：** 本人请求成功，跨用户、跨租户、伪造参数、失效身份和未授权代客被拒绝；Mock 登录生产关闭。

### 步骤 08：接入日志、链路与最小持久化审计

**前置：** 步骤05～07。

**做什么：**

1. 传递 request_id、correlation_id、trace_id、thread_id，记录真实主体、业务资源和脱敏结果。
2. 实现敏感字段脱敏，尤其是地址、联系方式、验证码、密钥及原始工具响应。
3. 为工具执行保存调用意图和完成结果；高风险操作使用前完成必要的持久化审计能力。
4. 预留统一指标采集点，后续业务只补充业务事件，不各自创建一套日志格式。

**产出位置：** infrastructure/observability/、审计用例/仓储、基础表迁移。

**如何验收：** 一次请求能串联 API、Agent 和 MCP；失败也有记录，敏感值不出现在日志、会话或审计摘要中。

### 步骤 09：实现订单查询 MCP

**前置：** 步骤06～08。

**做什么：**

1. 定义 OrderQueryPort、订单/支付快照及查询用例，先实现 MockOrderAdapter。
2. 提供本人有效订单、其他用户订单、不存在订单、支付未知及依赖失败等样例。
3. 注册 query_order、query_payment；处理器转换协议后调用用例，服务端先校验租户/身份/归属。
4. 启动一个独立 MCP HTTP 进程，由 API 侧客户端连接；此时只注册已实现工具，不伪装其他工具已经就绪。
5. 接入工具执行记录与统一只读重试预算，关闭客户端叠加隐式重试。

**产出位置：** 四层的 order 模块、MCP 客户端/服务器工厂、Mock 数据和契约测试。

**如何验收：** 直接通过 MCP 能获取正确订单/支付摘要；越权和不存在均按安全语义处理；故障恢复不突破重试预算。

### 步骤 10：完成第一条 Agent 对话闭环

**前置：** 步骤09。

**做什么：**

1. 实现单一 Supervisor、公共 State、受限意图路由、订单查询用例、工具执行和确定性结果守卫；仅触发异常时调用Reflection。
2. 定义 LLM/Tool 等端口，先用 Fake 模型验证确定性流程，再接入文档指定模型并实际验证模型标识、工具调用和响应兼容。
3. 模型可直接回答非业务寒暄，也可选择订单工具；不得入口硬编码每次都查订单。
4. 缺订单号时追问，工具无结果/失败时不编造；超过步骤或时限按契约结束。
5. 验证提示词加载的版本与文档一致，不擅自改写。

**产出位置：** application/agent/、模型适配器、POST /chat 入口及订单对话端到端测试。

**如何验收（M1）：** 用户询问本人 Mock 订单，真实模型通过 MCP 获取事实并回答；能追问、拒绝越权、处理失败。Fake 测试与真实模型验证分别记录。

### 阶段 B：会话与可靠运行

### 步骤 11：实现 Redis 会话与上下文隔离

**前置：** M1。

**做什么：**

1. 实现 SessionRepositoryPort、Redis 会话仓储和租户隔离 Key。
2. 保存经过脱敏的对话、Agent 结果与工具摘要，按既定 TTL 刷新规则读写。
3. 模型调用前由应用层组装上下文，可信身份不从会话消息恢复。
4. 实现生产失败关闭与开发显式内存降级，健康状态准确反映持久性。

**产出位置：** memory 应用模块、Redis 适配器、会话契约和集成测试。

**如何验收：** 相同授权会话能连续对话，跨租户/跨客户不能串历史；实例切换仍读同一 Redis 数据；降级不宣称已持久化。

### 步骤 12：实现 MySQL Checkpoint 与中断恢复

**前置：** 步骤10、11。

**做什么：**

1. 按《技术详细规格》11.1实现锁定 LangGraph 版本的 MySQLCheckpointSaver，持久化 State、元数据及 pending_writes。
2. 实现联合恢复键、父子版本、并发冲突、重复写入和事务回滚。
3. 在规定执行点保存进度，恢复时先核对已完成调用与工具执行记录，再决定后续动作。
4. 将数据库保存器通过 Bootstrap 注入，不在编排代码创建数据库客户端。

**产出位置：** checkpoint 表迁移、基础设施 Saver、CheckpointRepositoryPort、契约及恢复测试。

**如何验收：** 中途重启能恢复；重复保存不覆盖，冲突不会静默丢失；未提交节点写入可恢复，不因重启重复执行已有结果。

### 步骤 13：实现摘要、裁剪及长期记忆

**前置：** 步骤11、12；明确长期事实类别的剩余口径。

**做什么：**

1. 按唯一参数表实现摘要触发、原文保留窗口和每次模型调用前的 Token 预算检查。
2. 记录摘要覆盖范围，防止每轮重复追加旧消息；摘要失败使用裁剪兜底。
3. 实现 MySQL 用户画像、稳定事实提取、重要性及衰减清理；金额、实时业务状态与确认不作为长期记忆授权依据。

4. 按提示词执行“人工不可用→工单兜底→建单失败如实说明”，不编造编号。
5. 保存消息可见性，普通客户不能读取内部员工消息。

**产出位置：** ticket 四层模块、转接/工单表、事件及消费者。

**如何验收：** 建单和更新有真实结果；重复转接/兜底只建一次，双人接单仅一人成功；失败不伪造已接入或已提交。

### 步骤 28：补齐通知、审计及写操作故障恢复

**前置：** 步骤25～27。

**做什么：**

1. 将退款、改址、工单、转接、任务和知识事件接入真实 Outbox/Inbox 消费流程。
2. 实现 Mock 通知发送状态，处理 unknown 查询；通知失败不回滚已成功业务。
3. 故障注入确认消费、事务提交、发布确认、ACK与外部超时各个边界，核对幂等及审计恢复。
4. 确认消费者只能处理所属模块，不直接修改其他模块表。

**产出位置：** notification/audit 用例、消费者、恢复与故障注入测试。

**如何验收（M4）：** TC-78～TC-86涉及的可靠性约束通过，重复消息和重启不产生重复业务，高风险调用无自动重放。

### 阶段 E：客户与员工界面

### 步骤 29：实现客户聊天和会话页面

**前置：** Chat/API契约稳定，步骤10、11、15可用。

**做什么：**

1. 初始化 frontend/，建立 API 调用封装、登录态、错误展示和页面路由。
2. 实现发送消息、会话恢复、答案与必要来源、追问及人工处理状态展示。
3. 显示异步任务待处理与结果，通过原 task_id 查询，不重复发送原业务写请求。
4. 处理加载、无数据、无权限、失败和网络中断，不把接收成功当业务完成。

**产出位置：** frontend/src/pages/chat、api、auth、components及页面测试。

**如何验收：** 浏览器中能完成真实后端订单/物流/知识对话，刷新可恢复，身份失效安全退出，不泄露技术敏感信息。

### 步骤 30：实现退款和改址受控确认页面

**前置：** 步骤24～26、29。

**做什么：**

1. 退款展示服务端报价的订单、原因、金额、币种和有效期，用户明确确认并完成验证。
2. 地址表单独立提交新收件人、联系方式及完整地址，返回会话时仅带引用/摘要。
3. 展示过期、版本变化、待审核、结果未知和失败，按后端状态指引重新确认或查询。
4. 客服引导与客户本人确认使用分离身份，不通过前端参数冒充客户。

**产出位置：** frontend/src/pages/refund、order_address及确认组件。

**如何验收：** 无确认不能执行；按钮连点、刷新、网络超时和旧表单不会重复提交；完整地址不出现在对话上下文。

### 步骤 31：实现最小客服工作台

**前置：** 步骤07、25、27～30，FR-19范围已明确。

**做什么：**

1. 按《技术详细规格》第二十七章实现授权客户上下文、代客咨询、工单列表详情、人工队列和退款审核。
2. 员工专属查询/审核使用受控内部应用端口，不注册成新增模型工具。
3. 实现服务器分页、筛选、版本冲突、员工内容确认与接单幂等。
4. 切换客户清理前端临时上下文，不混用会话、任务或确认；普通客户不能访问员工界面数据。
5. 复用既有结果展示，不增加呼叫中心、绩效或运营大屏。

**产出位置：** frontend/src/pages/workbench、workbench HTTP路由、员工查询/命令用例。

**如何验收：** TC-87～TC-94通过；主管审核权限、客服范围、管理员非业务权限及内部消息隔离均在后端生效。

### 步骤 32：执行 Web 与 Agent 综合业务验收

**前置：** 步骤29～31。

**做什么：**

1. 用客户与员工两种入口执行订单、物流、三种知识路由、退款、改址、工单和转接。
2. 覆盖多轮追问、确认、复杂计划、失败恢复及异步完成，不只测试正常按钮路径。
3. 浏览器状态、API返回、数据库业务状态、审计和事件进行交叉核对。
4. 验证完整模型调用而非只用 Fake；记录模型、Prompt和知识版本。

**产出位置：** tests/e2e/及可复现的执行记录。

**如何验收（M5）：** Web、Agent和真实本地基础设施共同完成一期闭环；页面没有伪造完成状态，后台恢复与用户展示一致。

### 阶段 F：验收与交付

### 步骤 33：执行安全与数据隔离回归

**前置：** M5，各模块单元/契约/集成测试已通过。

**做什么：**

1. 覆盖跨租户、跨客户、跨团队、伪造身份、旧确认、重复写入、错误版本和非法状态。
2. 检查 Prompt注入、工具返回注入、任意Cypher及模型参数覆盖授权的拦截。
3. 检查工单内部消息、审计、事件、会话、Checkpoint和知识索引的敏感信息与访问边界。
4. 搜索硬编码凭据和未脱敏原始数据，验证生产关闭 Mock 登录/不允许静默内存降级。

**产出位置：** tests/安全用例与evals/safety，缺陷记录。

**如何验收：** 满足需求安全硬门槛；发现高风险误执行或越权必须修复，不以“测试环境”豁免业务校验。

### 步骤 34：执行检索、生成、Agent与性能评测

**前置：** 步骤33及冻结评测集。

**做什么：**

1. 按《技术详细规格》第十七章执行方法，测需求第十四章目标，不在测试脚本另设一套阈值。
2. 分别测RAG双路候选、最终排序、KG关系和混合证据；核对版本一致性与无依据拒答。
3. 测多步骤选择、停止、恢复及人工处理，保留错误问题与对应工具/状态证据。
4. 按既定预热、并发和统计窗口压测，区分普通请求、异步受理及实际任务完成延迟。
5. 未达目标时定位模型、Embedding、数据库、检索或队列瓶颈，修复后只复测受影响项及必要回归。

**产出位置：** evals/各执行目录和reports；引用data/manifests中的数据版本清单，并记录本次模型、Prompt、工具契约和环境版本。

**如何验收：** 报告有版本、分子、分母、实测值、错误样本和统计窗口；未达标项如实记录，初始目标不能写成已实现。

### 步骤 35：完成容器部署与恢复演练

**前置：** 功能、契约与安全验证通过。

**做什么：**

1. 打包已锁定依赖及受控模型资源，分别运行前端、API、单个MCP服务和Worker。
2. 显式部署迁移任务、注入各进程最小权限凭据与模型/存储配置，不将密钥固化到镜像。
3. 验证启动顺序、健康就绪、断连、实例重启、队列积压、DLQ及Checkpoint恢复。
4. 演练兼容升级和回滚，确保旧消息/未完成任务不因代码替换丢失。
5. 本地模拟交付不等于生产上线；企业接入、生产灰度及回滚阈值在真实部署前另行确认，不擅自对外发布。

**产出位置：** Dockerfile、docker-compose.yml、deploy/以及部署演练记录。

**如何验收：** 清洁环境按指南可复现，重启不丢已承诺持久化的数据；回滚不重复高风险操作。生产目标需有真实环境验证依据。

### 步骤 36：交付文档、验收映射与实际启动命令

**前置：** M1～M5及步骤33～35形成完整证据。

**做什么：**

1. 按现有FR/BR/TC逐项回填实现位置、测试结果和例外，不只写“全部完成”。
2. 将开发运行指南里的设计命令更新为实际安装、初始化、启动、测试、评测和故障恢复命令。
3. 更新项目目录结构为实际实现，标明仍未创建或不在一期范围的内容，不保留误导性完成描述。
4. 将剩余缺陷、未达目标与真实企业适配差异列明；功能、可靠性、安全与指标分别记录。
5. 确认源码、模拟数据、迁移、配置示例、锁文件、测试和评测产物可随交付复现，不含真实敏感信息。

**如何验收（M6）：** 按文档可以从安装到运行再到验收复现；一期功能没有漏项，安全问题已关闭，未验证的生产能力没有被写成已完成。

## 五、每个业务模块采用同一落地顺序

| 顺序 | 做什么 | 检查重点 |
| --- | --- | --- |
| 1 | 从 FR/BR/TC提取模块输入、输出与失败场景 | 不自行添加业务默认值或删除边界 |
| 2 | 定义纯领域对象、值对象和确定性规则 | 不依赖模型、数据库、传输框架 |
| 3 | 定义应用用例、端口、DTO及授权/事务协调 | 用例可注入Fake，身份来自可信上下文 |
| 4 | 实现Mock/数据库/企业或检索适配器 | 替换技术不改变业务契约，可靠写入必须持久化 |
| 5 | 添加HTTP/MCP/消息入口及Bootstrap装配 | 接口不绕过用例，模型只获得授权工具 |
| 6 | 完成有意义的单元、契约、集成和端到端验证 | 正常、越权、失败、并发、幂等及恢复均有依据 |
| 7 | 接入Agent/页面并记录验收结果 | 最终用户可用，而不仅是内部函数运行成功 |
