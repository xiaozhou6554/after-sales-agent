# 企业智能售后服务 Agent｜需求摘要

版本：v1.8　基线：2026-10-19　状态：待重新开发

本文件是业务范围摘要与导航。业务范围、业务规则和验收口径以[需求详细规格](需求详细规格.md)为准；技术实现以[技术详细规格](技术详细规格.md)为准；多系统概念阅读入口见[多系统本体设计](多系统本体设计.md)。摘要不得覆盖详细规格。业务变更须先更新对应详细规格，再同步本摘要并记录版本。

## 项目目标

建设可运行、可审计、私有化部署的售后 Agent。它能跨商品、订单、物流、售后、仓储、支付、知识和工单系统查询/执行获授权的业务流程，并让主管用统一口径分析退货和退款。开发环境使用隔离、显式标记的模拟系统；生产通过企业适配器连接真实系统。项目当前只保留 `docs/` 与 `data/`，无可启动代码。

## 用户与权限

| 用户 | 能做什么 | 边界 |
| --- | --- | --- |
| 客户 | 查本人售后；确认申请、退款和改址 | 只能操作本人有权订单；不得提供验证码给模型 |
| 客服/人工客服 | 授权代客查询、处理工单 | 不代替客户确认高风险操作 |
| 售后主管 | 审核退款、查团队数据、调查异常 | `refund:review` 与 `analytics:read` 分权；不自动获得支付权 |
| 仓储员工 | 登记收货和验收 | 仅授权仓库范围及 `warehouse:receive/inspect` |
| 运维人员 | 调查服务和依赖异常 | 仅 `incident:read` 与获授权系统范围 |
| 支付执行服务 | 满足条件后调用原支付渠道退款 | 独立服务身份、凭证和审计；模型无执行工具 |

## 一期范围

- 售后知识 RAG/KG/混合查询，订单与支付状态查询、物流、工单和人工转接。
- 多系统本体和ID/状态映射；分批退货收货、验收、部分退款、受控原路退款执行、回调和对账。
- 主管查询产品退货件数率、退款明细率、退款金额率；支持数据质量和证据下钻。
- 通用异常调查：业务指标异常、跨系统事实不一致、技术运行故障。
- 聊天、必要确认及最小客服/仓储/主管工作台；授权、幂等、Outbox/Inbox、审计与故障恢复。

不做自建支付清算、订单取消、完整CRM/呼叫中心、员工绩效管理或未经审核的第三方接入。支付渠道执行由受控服务完成；生产接入要有具体系统契约及独立验收。

## 关键业务约束

退款审核、仓储退货验收和资金执行分别记录 `review_status`、`return_status`、`funds_status`。审核通过不等于退货完成或退款成功。支付成功须有权威渠道证据；超时为未知，按原执行ID查询，不盲目补发或释放预留。模型不得执行仓储写入或支付。

产品、SKU、订单明细、退货验收和退款分摊使用跨系统可追溯的canonical ID；映射有版本与有效期。同名不自动合并。动态业务事实留在权威系统，统计缺源、映射歧义、分摊不平或对账差异时不能按0处理或作完整排名。

异常调查固定范围、时间窗、数据快照、版本与证据。它可以定位数据错误、跨系统冲突、链路首个失败点及有统计贡献的候选因素；相关性不能自动定性为因果根因，证据不足时须明确未确认。

## 需求目录与验收

完整FR-01～FR-24及详细条款见[需求详细规格](需求详细规格.md)。新增范围集中为：FR-20本体与映射、FR-21仓储、FR-22退款执行、FR-23产品售后指标、FR-24全业务异常追查。

验收总表保留在详细规格：TC-01～TC-94覆盖售后与工作台；TC-95～TC-109覆盖本体/仓储/支付/分析；TC-110～TC-123覆盖全域异常诊断与追查；TC-124～TC-128补充知识检索边界。v2数据将场景映射至需求与结构化预期；功能目前均未实现，静态校验不作为运行通过证据。

## 开发顺序

先冻结本体、权限与跨系统契约，再准备v2模拟数据；之后实现授权与审计、订单/售后、仓储、支付执行与对账、本体投影、指标分析和异常调查，最后完成工作台、故障/安全验收及生产适配评估。详细步骤见[项目开发流程](项目开发流程.md)，目标目录见[项目目录结构](项目目录结构.md)。
