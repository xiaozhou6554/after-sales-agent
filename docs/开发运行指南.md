# 企业智能售后服务 Agent 开发运行指南

## 一、环境要求

| 组件 | 版本要求 | 说明 |
| :--- | :--- | :--- |
| 操作系统 | Windows、macOS 或 Linux | Windows 推荐使用 PowerShell 或 WSL2 |
| Python | 3.10.x | 项目约束为 `>=3.10,<3.11`，推荐使用 Conda 的 `model` 环境 |
| Conda | Miniconda 或 Anaconda | 用于隔离 Python 依赖 |
| Docker Engine | 20.10 及以上 | 用于运行 MySQL、Redis、RabbitMQ、Neo4j 及可选 WooCommerce |
| Docker Compose | v2 及以上 | 使用 `docker compose` 命令 |
| MySQL | 8.4 | 项目业务库，由 Compose 启动 |
| Redis | 7.4 | 会话与短期状态，由 Compose 启动 |
| RabbitMQ | 3.13 | Outbox 事件投递，由 Compose 启动 |
| Neo4j | 5.26 Enterprise | 本地知识图谱；使用前确认许可证配置 |
| Node.js | 24.x | 仅前端测试需要 |
| WooCommerce | WordPress + WooCommerce REST API v3 | 可选本地联调环境；退款写入默认为非支付网关记录 |

## 二、依赖管理

```bash
conda create -n model python=3.10 -y
conda activate model

# 安装项目及开发、测试依赖
python -m pip install -e ".[dev]"

# 或者只安装运行依赖
python -m pip install -e .

# 检查依赖是否完整
python -m pip check
```

前端测试使用 Node.js，在 `frontend` 目录执行 `npm install`（仓库提供 lock 文件时优先使用 `npm ci`）。

## 三、配置说明

首次配置时复制 `.env.example` 为 `.env`；如果 `.env` 已存在，不要覆盖。将本机密钥填入 `.env`，不要提交密钥或把密钥粘贴到日志中。常用配置包括：

- `APP_ENV`：开发环境使用 `development`。
- `MYSQL_URL`、`REDIS_URL`、`RABBITMQ_URL`：本地基础设施连接地址。
- `NEO4J_URI`、`NEO4J_USERNAME`、`NEO4J_PASSWORD`：本地知识图谱连接信息；只读账号另由 `NEO4J_QUERY_*` 配置。
- `LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY`：模型供应商及凭据。
- `ADDRESS_ENCRYPT_KEY`：地址加密密钥；生产环境必须换成专用强密钥。
- `VECTOR_BACKEND`：本地默认使用 `chroma`。

已有 Docker 数据卷不会因为修改 `.env` 中的数据库密码而自动更新账号密码。不要通过删除数据卷来绕过连接问题。

### 本地 WooCommerce 联调

1. 按“启动流程说明”单独启动 WooCommerce Compose 服务，并打开 `http://localhost:8088` 完成 WordPress 初始化。使用一组仅供本机的强管理员密码；本地默认值只适用于隔离的开发环境。
2. 在 WordPress 后台安装并启用 WooCommerce，完成商店向导；使用测试商品和测试订单，不配置真实支付网关。
3. 在 WooCommerce 后台进入“设置 → 高级 → REST API”，创建具备 `Read/Write` 权限的密钥。将 Consumer Key 和 Consumer Secret 写入 `.env` 的 `WOO_CONSUMER_KEY`、`WOO_CONSUMER_SECRET`。

   本机 HTTP 联调使用 OAuth 1.0a 签名，HTTPS 使用 Basic Auth；适配器不会把密钥放进 URL 查询参数。
4. 在 `.env` 配置 `WOO_STORE_URL=http://localhost:8088`、`WOO_TEST_ORDER_ID` 和 `WOO_TEST_TENANT_ID`。被测订单必须在 WooCommerce `meta_data` 中带有 `after_sales_tenant_id`，可选带有 `after_sales_customer_id`；适配器只在租户值匹配时返回订单。
5. 若要让聊天 Agent 查询 WooCommerce 订单/支付快照，在 `.env` 显式设置 `WOO_ORDER_QUERIES_ENABLED=true`，并配置上述 REST 密钥；重启 MCP 服务后生效。订单编号需使用 WooCommerce 数字 ID，订单元数据需匹配租户和售后客户 ID。此开关只替换订单/支付只读查询适配器；物流、退款审核/执行仍使用项目现有本地实现，不代表真实支付退款已经接通。
6. 默认 `WOO_ENABLE_REFUND_WRITE=false`，联调只读取订单。需要验证退款记录接口时，先选定可修改的本地测试订单，再填写 `WOO_TEST_REFUND_AMOUNT` 并显式设置 `WOO_ENABLE_REFUND_WRITE=true`。
7. 执行定向验收：

   ```bash
   python -m pytest tests/unit/test_woocommerce_adapter.py tests/integration/test_woocommerce_live.py -q
   ```

   在线用例未配置必需的 `WOO_*` 变量时会跳过；配置后先核对订单和租户。退款写入通过 `POST /orders/{id}/refunds` 调用，强制传入 `api_refund=false`、`api_restock=false`，并用退款元数据键避免重复创建。该操作只创建 WooCommerce 的退款记录，不代表支付渠道已退回资金。WooCommerce REST API v3 提供订单查询和订单退款端点；`api_refund` 为 `true` 时才会调用支付网关。[订单 API](https://developer.woocommerce.com/docs/apis/rest-api/v3/orders/) · [退款 API](https://developer.woocommerce.com/docs/apis/rest-api/v3/order-refunds/) · [REST API 认证](https://developer.woocommerce.com/docs/apis/rest-api/authentication/)。

#### 坐席代客查询 WooCommerce 订单

订单元数据和工作台客户选择必须对应同一个售后客户。例：开发坐席 `support-north-01` 的租户为 `tenant-north`，其 fixture 授权范围包含 `CUSTOMER-01`；下例将 WooCommerce 测试订单归属到该客户。请只使用本地测试商店和测试订单。

1. 按前面的说明启动项目基础设施、WooCommerce 商店、MCP 和 API；在 WooCommerce 中创建一笔测试订单。记录订单 REST 资源的**数字 ID**（不是可能被自定义的订单展示编号）。
2. 给这笔订单写入售后租户和客户元数据。推荐通过 WooCommerce REST API 更新订单：在 Postman 或其他 REST 客户端中选择 OAuth 1.0a 认证，填入本地 WooCommerce REST `Read/Write` 密钥；对 `http://localhost:8088/wp-json/wc/v3/orders/{数字订单ID}` 发送 `PUT`，请求体为：

   ```json
   {
     "meta_data": [
       {"key": "after_sales_tenant_id", "value": "tenant-north"},
       {"key": "after_sales_customer_id", "value": "CUSTOMER-01"}
     ]
   }
   ```

   本地 HTTP 商店使用 OAuth 1.0a 签名；密钥放在 REST 客户端的认证配置中，不要把 Consumer Secret 粘贴到 URL、截图或日志。更新后可对同一订单发送 `GET` 并检查响应的 `meta_data`，确认两个键和值均已保存。不要直接改 WooCommerce 数据库。
3. 在项目 `.env` 中设置 `WOO_ORDER_QUERIES_ENABLED=true`、`WOO_TEST_TENANT_ID=tenant-north`、`WOO_TEST_ORDER_ID={上一步的数字订单ID}`，并确保 `WOO_STORE_URL`、`WOO_CONSUMER_KEY`、`WOO_CONSUMER_SECRET` 指向该本地商店。`WOO_TEST_TENANT_ID` 必须与订单 `after_sales_tenant_id` 完全一致。保存后重启 MCP，使新配置生效；API 也需正常运行。
4. 浏览器使用员工账号 `support-north-01` 登录，进入“工单工作台”。下拉选项会显示脱敏名称和已授权的内部客户编号，例如 `客户 CUS*** · CUSTOMER-01`。选择编号与订单 `after_sales_customer_id` 完全一致的客户（本例为 `CUSTOMER-01`），等工作台完成切换/刷新后点击“开始代客咨询”。客户列表由服务端按坐席身份和租户授权返回；没有列出的客户不能通过手工输入 ID 加入授权范围。
5. 进入该客户对应的服务会话后，询问本订单状态并提供 WooCommerce 数字订单 ID。会话使用工作台保存的客户授权上下文；不要在浏览器请求、会话存储或聊天内容外伪造 `customer_id`。如切换了客户，回到工作台重新选择目标客户并重新开始代客咨询，再查询对应订单。

查询被拒绝或显示订单不存在时，按顺序核对：REST API 的 `GET` 是否能读到该订单；`WOO_TEST_ORDER_ID` 是否为数字资源 ID；`WOO_TEST_TENANT_ID` 与 `after_sales_tenant_id` 是否完全相同；工作台当前选择的售后客户 ID 是否与 `after_sales_customer_id` 相同；账号是否能在客户下拉框中看到该客户；配置变更后 MCP 是否已重启。缺少 `after_sales_customer_id` 时，适配器会回退使用 WooCommerce 原生 `customer_id`，它通常不是项目的售后客户 ID，因此建议始终显式写入售后客户元数据。租户不匹配时适配器会按权限规则隐藏该订单，不能通过更改坐席会话上下文来绕过。

## 四、启动流程说明

项目基础设施和 WooCommerce 本地商店是两套独立服务：项目基础设施为 Agent 提供 MySQL、Redis、RabbitMQ 和 Neo4j；WooCommerce 是可选的本地电商测试商店。项目 MySQL 使用本机 `3306`，WooCommerce 专用 MariaDB 使用 `3307`，WordPress 使用 `8088`。WooCommerce 不启动 Agent 的 API/MCP，也不写入项目 MySQL。

以下两套流程各自完整，从头按所选场景执行，不需要跨场景跳转。仅在需要真实联调 WooCommerce 订单时选择场景 B。

### 场景 A：不联调 WooCommerce，只启动售后 Agent

#### A1. 准备终端和配置

打开第一个 Windows PowerShell 窗口：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
```

确认项目根目录 `.env` 已存在。若不存在，从 `.env.example` 复制一份；若已存在，只编辑需要的配置，不要覆盖。保持以下开关关闭；不需要 WooCommerce 地址、REST 密钥或订单元数据：

```dotenv
WOO_ORDER_QUERIES_ENABLED=false
```

#### A2. 启动 Agent 基础设施并迁移数据库

仍在第一个窗口执行：

```powershell
# 启动 Agent 所需的 MySQL、Redis、RabbitMQ 和 Neo4j
docker compose up -d

# 查看容器和健康状态
docker compose ps

# 检查应用配置能否连接上述服务
python -m bootstrap.infrastructure_check

# 应用尚未执行的数据库迁移
python -m bootstrap.migrate apply
```

这些命令只启动 Agent 的基础设施；它们不会启动 MCP、API 或 worker。检查失败时先按错误信息解决服务或 `.env` 配置问题，再继续。

#### A3. 启动 MCP 工具服务

打开第二个 PowerShell 窗口，MCP 会以前台方式运行并显示日志；保持此窗口打开：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
python -m bootstrap.mcp_main
```

MCP 为 API 提供订单、知识等工具；本场景中订单查询使用项目默认 Mock 适配器。

#### A4. 启动 API 和前端入口

打开第三个 PowerShell 窗口，保持运行：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
python -m bootstrap.api_main
```

API 默认监听本机 `8000` 端口，为浏览器提供页面和 HTTP 接口。访问 `http://127.0.0.1:8000`。若启动时提示端口已占用，先检查服务是否已经运行：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health/live
```

返回 `alive` 表示 API 已运行，不要再启动重复进程。手动启动的 MCP 和 API 不会列在 `docker compose ps` 的容器列表中。

#### A5. 登录并使用

使用开发员工账号 `support-north-01` 登录。坐席代客咨询前，进入“工单工作台”，先选择当前账号已授权的客户，再点击“开始代客咨询”。本场景不需要启动 WooCommerce 容器。普通同步聊天不需要 worker；若勾选聊天框的“后台处理”，则需要按后文说明启动 worker 来处理后台聊天任务。

### 场景 B：联调 WooCommerce 订单

本场景包含场景 A 的全部 Agent 启动步骤，并额外启动 WooCommerce 商店、创建测试订单及配置查询适配器。每个新开的 PowerShell 窗口都要激活 `model` 并进入项目目录。

#### B1. 准备第一个终端和项目配置

打开第一个 Windows PowerShell 窗口：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
```

确认项目根目录 `.env` 存在。已有 `.env` 时不要覆盖；本场景稍后需要在其中填入 WooCommerce REST 密钥。

#### B2. 启动 Agent 基础设施并迁移数据库

仍在第一个窗口执行。此步骤启动的是 Agent 的 MySQL、Redis、RabbitMQ 和 Neo4j，与 WooCommerce 数据库分开：

```powershell
docker compose up -d
docker compose ps
python -m bootstrap.infrastructure_check
python -m bootstrap.migrate apply
```

`infrastructure_check` 用于确认服务连接正常；`migrate apply` 应在 MCP/API 启动前完成。

#### B3. 启动 WooCommerce 专用数据库和 WordPress

仍在第一个窗口执行：

```powershell
# 启动 WooCommerce 专用 MariaDB（本机 3307）和 WordPress（本机 8088）
docker compose -f docker-compose.woocommerce.yml up -d woocommerce-db wordpress

# 一次性安装 WordPress 和 WooCommerce 插件；--rm 只删除初始化容器，保留命名数据卷
docker compose -f docker-compose.woocommerce.yml --profile setup run --rm wp-cli

# 查看 WooCommerce 服务状态
docker compose -f docker-compose.woocommerce.yml ps
```

打开 `http://localhost:8088`，用 WooCommerce Compose 配置的本地管理员账号进入后台。首次使用完成本地商店向导，创建测试商品和测试订单；不要设置真实支付网关。不要对该 Compose 项目运行 `down -v`，否则测试商店和订单数据卷会被删除。

#### B4. 创建 REST API 密钥并给订单写入售后归属

在 WordPress 后台进入“WooCommerce → 设置 → 高级 → REST API”，新建 `Read/Write` 密钥。创建或选择一笔测试订单，记录 WooCommerce REST 资源的数字订单 ID（不是可自定义的展示编号）。

用 Postman 或其他 REST 客户端配置 OAuth 1.0a，对 `http://localhost:8088/wp-json/wc/v3/orders/{数字订单ID}` 发送 `PUT`，请求体示例：

```json
{
  "meta_data": [
    {"key": "after_sales_tenant_id", "value": "tenant-north"},
    {"key": "after_sales_customer_id", "value": "CUSTOMER-01"}
  ]
}
```

本地 HTTP 商店使用 OAuth 1.0a 签名。Consumer Secret 只填在 REST 客户端的认证配置中，不要放进 URL、截图或日志。再用 `GET` 检查订单的 `meta_data`，确认两个键和值都已保存。示例中的租户和客户对应开发坐席 `support-north-01` 可访问的 `CUSTOMER-01`。不要直接修改 WooCommerce 数据库。

#### B5. 配置 Agent 使用 WooCommerce 查询

编辑项目根目录 `.env`，填入刚才生成的真实密钥，并保持退款写入关闭：

```dotenv
WOO_STORE_URL=http://localhost:8088
WOO_ORDER_QUERIES_ENABLED=true
WOO_CONSUMER_KEY=实际的ConsumerKey
WOO_CONSUMER_SECRET=实际的ConsumerSecret
WOO_ENABLE_REFUND_WRITE=false
```

`WOO_ORDER_QUERIES_ENABLED=true` 让 MCP 使用 WooCommerce 读取订单/支付快照；`false` 则使用项目默认 Mock 适配器。运行在线集成测试时还可设置 `WOO_TEST_ORDER_ID` 为上一步的数字订单 ID、`WOO_TEST_TENANT_ID=tenant-north`。这些是在线测试参数，不取代坐席会话中的客户授权上下文。保存 `.env` 后再启动 MCP；若 MCP 已运行，先在其窗口按 `Ctrl+C` 停止，再重新启动以加载新配置。

#### B6. 启动 MCP 工具服务

打开第二个 PowerShell 窗口并保持运行。MCP 启动时读取 `.env` 中的 WooCommerce 查询开关和密钥：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
python -m bootstrap.mcp_main
```

#### B7. 启动 API 和前端入口

打开第三个 PowerShell 窗口并保持运行：

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
python -m bootstrap.api_main
```

API 默认监听本机 `8000` 端口。打开 `http://127.0.0.1:8000`。如果提示端口占用，执行 `Invoke-RestMethod http://127.0.0.1:8000/health/live`；返回 `alive` 表示服务已运行，不要再启动重复 API。手动运行的 MCP/API 不会显示在 Docker 容器列表中。

#### B8. 以坐席身份验证订单查询

使用 `support-north-01` 登录，在“工单工作台”的“当前授权客户”中按可见编号选择 `CUSTOMER-01`（选项示例：`客户 CUS*** · CUSTOMER-01`），再点“开始代客咨询”。进入该客户对应的会话后，询问测试订单状态并提供 B4 记录的 WooCommerce 数字订单 ID。

> **注意：** 场景 B 启用 WooCommerce 查询时，必须使用本地商店中真实存在的数字订单资源 ID，例如 `123`（仅为格式示例，请换成自己的订单 ID）。`ORDER-001` 是项目 Mock 数据编号，不是 WooCommerce 订单 ID，在场景 B 下会查不到。只有场景 A 使用项目 Mock 订单数据时才使用 `ORDER-001`。页面右上角的“已连接”只表示浏览器连上 Agent API，不代表 WooCommerce REST API 已经连通。

订单 `after_sales_tenant_id` 必须与请求租户一致，`after_sales_customer_id` 必须与工作台所选客户一致。客户选项由服务端授权列表提供，不能通过手改客户 ID 绕过权限。若查询不到，检查 REST API 的 `GET`、数字订单 ID、`.env` 地址/密钥/开关、两个订单元数据值及 MCP 是否已在配置修改后重启。缺少 `after_sales_customer_id` 时，适配器会退回 WooCommerce 原生 `customer_id`，通常与售后客户 ID 不同，因此应显式设置。

### 可选：启动后台任务与 Outbox worker

聊天框“后台处理”勾选后，API 会受理并持久化 `agent.chat` 任务，前端随即轮询任务状态；`worker_main` 负责消费任务事件并运行聊天。若没有 worker，任务可能保持 `pending`，页面就会一直显示“正在处理，请稍候”。普通同步聊天（不勾选“后台处理”）不需要 worker。

同一个 worker 还会发布项目 Outbox，并消费异步通知、退款审核等事件。因此只有确实要验收后台聊天或异步事件时才启动；启动前确认待处理事件和副作用符合当前测试计划，不要为了普通订单问答启动 worker。

```powershell
conda activate model
cd "D:\个人总结\实战计划\企业智能售后服务Agent"
python -m bootstrap.worker_main
```

### 停止 WooCommerce 商店

仅在场景 B 使用后需要停止商店时，在项目目录执行以下命令。它会停止 WooCommerce 容器并保留商店数据；下次联调重新执行场景 B 的 B3 即可。不要使用 `down -v`，否则会删除 WooCommerce 数据卷。

```powershell
docker compose -f docker-compose.woocommerce.yml stop
```

### 开发测试账号登录

2. 客服账号进入“工单工作台”后，先从服务端返回的授权客户列表中选择客户，再点击“开始代客咨询”。不能通过手动填写 `customer_id` 扩大授权范围。
3. 主管、仓储、运维和管理员账号只验证各自实际授予的 Scope；没有对应权限时，功能应被拒绝或显示无权限状态，不能用更换前端账号信息绕过。
4. `svc-pay-north-01`、`svc-ontology-north-01`、`svc-analytics-north-01`、`svc-supervisor-north-01`、`svc-investigation-north-01` 是后端服务身份，用于受控服务调用，不是员工或客户的交互登录账号。
5. 表中账号仅用于隔离的本地开发/测试环境，不是企业正式账号。生产接入前仍须对接并验收企业 IdP、角色映射和正式授权范围。

### 使用坐席工作台

基础设施、MCP 服务和 API 均启动后，在浏览器打开 `http://127.0.0.1:8000`，使用开发环境的员工测试账号登录，再进入“工单工作台”。工作台按当前坐席授权范围读取客户和工单；先选择客户，再从左侧服务队列打开工单。中间区域展示工单描述和服务记录，右侧展示工单状态、人工协作队列与退款审核入口。

坐席代客咨询前，必须先在“工单工作台”选择一个当前授权客户，再点击“开始代客咨询”。客户下拉项会显示脱敏名称和已授权的内部客户编号；联调 WooCommerce 时按订单的 `after_sales_customer_id` 选择相同编号。直接在未选客户的新会话中发送消息会被页面拦截并提示先选择客户，避免请求缺少客户授权上下文。客户测试账号可直接进入服务对话。

工作台的分派、状态变更、人工接单和退款审核仍通过现有服务端接口执行，并遵循原有权限、版本与确认校验。若没有工单、人工队列或退款权限，页面会显示相应空状态；页面不会用演示数据伪装模型分析或服务端结论。点击“开始代客咨询”可进入服务会话。
